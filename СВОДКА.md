- Кластерные обрывы в утренние (09:00-09:07) и вечерние (22:00-22:20) часы

- DeepSeek, MiniMax — все провайдеры дропают >40K в час-пик

- DB: 14M → 29M за 24ч после gateway restart (FTS5 пересоздание)


### Инсайты и выводы

- Stream Stale — кластерный эффект, не provider-specific баг. Когда ≥2 cron-джобы с контекстом >40K токенов запускаются одновременно, провайдер обрывает стрим

- retry механизм компенсирует: джоба выполняется со 2-й попытки. Это не провал, а штатное поведение при высокой нагрузке

- FTS5 фрагментация происходит даже без trigram — стандартный porter FTS5 тоже пересоздаётся при gateway restart и фрагментирует DB. VACUUM сжал до 14M, через 24ч → 29M


### Трудности и решения

- Алерт на системное ограничение: Stream Stale при >40K — не баг, а особенность. Симптом: ложные алерты. Решение: различать «баг» и «ограничение»


### Рекомендации на будущее

- Stream Stale при >40K в час-пик — не алерт. Алёртить только если retry НЕ сработал

- FTS5 фрагментация после gateway restart неизбежна — VACUUM раз в неделю


### Количественные результаты

- Stream Stale алертов: с тревожных до информационных

- DB: 14M → 29M → 14M (после VACUUM)


### Предложения по улучшению

- Перенести анализ Stream Stale из «ошибок» в «ожидаемое поведение»

- Добавить еженедельный VACUUM после gateway restart

### Инсайты и выводы

### Инсайты и выводы

- **две параллельные fallback-системы** (`fallback_providers` (новый) + `fallback_model` (legacy)) конфликтуют — если `fallback_providers` в неверном формате (YAML-объект вместо массива), код Hermes читает пустой chain и падает на google2 (хардкод-резерв), игнорируя локальный mlx-local. Ошибка конфига давала ложное ощущение «есть fallback»

- **stderr vs stdout** — cron-планировщик для `no_agent` читает только stdout. Если скрипт пишет всё в stderr (как `imsg`), cron-логи всегда показывают «silent (empty output)» — невозможно отличить «нет новых данных» от «скрипт упал»

- **macOS TCC (Transparency, Consent, Control)** — процессы получают разрешения по цепочке запуска. Hermes.app не имеет Full Disk Access, поэтому его дочерние процессы (cron) не могут читать `~/Library/Messages/chat.db` через `imsg`, хотя сам бинарник Hermes Python-процесса имеет FDA

- `session_search` **не фильтрует** archived-сессии — они в той же FTS5-индексации. Из 1200+ сессий 66 archived, но поиск по ним работает


### Трудности и решения

- «Пустой stdout = нет данных» — молчаливое предположение, что всё в stdout. Если утилита пишет в stderr, cron-планировщик для `no_agent` видит пустой результат. Всегда проверять оба потока

- «Legacy-ключ не мешает» — `fallback_model` (legacy) не удалён при миграции на `fallback_providers`. Legacy-ключ переопределял логику, хотя визуально «есть новые настройки»

- «Одна ошибка = одна причина» — два независимых бага (формат fallback + TCC-доступ) вызывали одинаковый симптом (silent fail). Расследование каждой джобы по отдельности не вскрыло бы системную проблему


### Рекомендации на будущее

- При расследовании cron-сбоев: **сначала проверять формат конфига** (YAML-структуру), а не DNS/VPN/баланс. Смотреть оба ключа fallback + legacy

- **Всегда писать stdout в cron-скриптах.** Если данные идут в stderr — cron не видит результат. Явный `print()` или `sys.stdout.write()`

- При TCC-проблемах (Mac): заменить внешнюю утилиту (`imsg`) на прямой SQLite-запрос — Python с FDA читает `chat.db` напрямую, даже если порождённый процесс не имеет FDA

- При анализе сбоев: не доверять одному источнику (логам cron). Проверять: (1) прямой curl API, (2) Python-клиент OpenAI, (3) конфиг Hermes, (4) логи запуска cron

Это не «ещё один способ», а принципиально иной цикл: headless Chrome сохраняет state между вызовами, тогда как `browser_console` убивает fetch/cookie каждым вызовом.

- **fetch-DOMParser одним вызовом на все воронки** — цикл `for (const id of IDS)` + DOMParser в ОДНОМ `evaluate_script` собирает все 18 воронок за 1 вызов вместо 15+ навигаций. Это меняет архитектуру масштабирования: с N аккаунтов × 5 вызовов → N аккаунтов × 1 вызов.

- **изолированный контекст Chrome (`isolatedContext`) для параллельных сессий** — позволяет работать с несколькими аккаунтами одновременно без конфликтов cookie. Без этого один login-редирект ломает все остальные сессии в контейнере.


### Трудности и решения

- `browser_console` + fetch = 401/403. Симптомы: fetch внутри `browser_console` возвращает ошибку авторизации; `browser_console` блокирует cookie. Симптом: 403 на `/api/v4/*`. Решение: `mcp__chrome_devtools__evaluate_script`.

- Параллельные сессии в одном Chrome → `isolatedContext`. Симптомы: login в один аккаунт редиректит все сессии на последний. Симптом: данные одного аккаунта появляются в сессии другого. Решение: `new_page` с `isolatedContext`.


### Рекомендации на будущее

- НЕ использовать `browser_console` для fetch — всегда `mcp__chrome_devtools__evaluate_script`.

- Для многовороночных аккаунтов — fetch-DOMParser одним вызовом на все ID, НЕ навигация по каждой воронке отдельно.

- При >500 сообщений в сессии — промежуточный отчёт каждые ~200 сообщений, иначе risk session_timeout.

- При free-тарифе amoCRM — верифицировать «одна воронка» тройным сигналом, НЕ доверять dropdown alone.
