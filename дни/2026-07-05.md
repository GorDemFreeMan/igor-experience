## Инсайты и выводы

- гибридный парсинг amoCRM без API и экспорта — это комбинация трёх слоёв: (1) `AMOCRM.data.current_list` для структурированных полей (ФИО, дата), (2) DOM-обход `a[title]` для полных телефонов, которых нет в JS-модели, (3) прямая URL-пагинация вместо AJAX-кликов. Каждый слой компенсирует слепые зоны другого.

- AJAX-пагинация через `browser_console` не масштабируется >10 страниц — сессия браузера деградирует (~60с на страницу), а прямая URL-навигация (page=N в URL) работает стабильно на 100+ страниц.

- при поиске товаров в СПб критично фильтровать по модели устройства (A3526 vs A3257) — eSIM-only версии iPhone 17 Pro Max визуально неотличимы от dual-SIM, но функционально непригодны для РФ.


## Трудности и решения

- Пустой snapshot после редиректа в amoCRM (#28): `browser_navigate` на smileroom → snapshot пустой, хотя консоль показывает успешный рендеринг. Решение: после редиректа всегда проверять `browser_console` с `document.querySelector('.list-row')` — если элементы есть, работать через консоль, не через snapshot.

- AJAX-пагинация на >10 страниц: каждый `browser_click` по кнопке «Следующая» добавляет ~3-5с задержки, на 20+ страницах сессия нестабильна. Решение: прямая URL-навигация (`?page=N`) через `browser_navigate`.


## Рекомендации на будущее

- При парсинге amoCRM через браузер на >1000 записей: начинать с `AMOCRM.data.current_list` для получения структуры полей, затем дополнять DOM-данными через `browser_console` с `document.querySelectorAll`. НЕ начинать с DOM — потеряешь системные поля.

- При поиске iPhone в РФ: первым делом проверять модель (A-номер) — физическая SIM критична. Фильтровать eSIM-only на этапе сбора, а не постфактум.

- При обновлении amoCRM-скиллов после большой сессии парсинга: документировать pitfall'ы сразу (баг #28 — пустой snapshot после редиректа, pitfall #27 — 22K контактов на smileroom).
