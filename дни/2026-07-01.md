## Инсайты и выводы

- state.db FTS trigram corruption — не изолированное явление, а эскалационный процесс: trigram bloat → partial FTS unavailability (no such table) → полная malformation (database disk image is malformed). Каждый gateway restart ускоряет эскалацию.

- integrity_check после VACUUM ≠ здоровье FTS5. 14.06 уже фиксировали этот разрыв, но 01.07 он проявился в полную силу. Нужна двухфазная проверка: integrity_check → FTS content-query на известных записях.

- горячий бэкап (hot backup) за 1 минуту до коррупции — критический фактор восстановления. Бэкап 19:36 (38MB) предшествовал malformation в 22:00 — .dump core tables из него сработал.

- Stream Stale кластер (4 события за 17 минут) — не случайность, а системный эффект при перегрузке DeepSeek API в утренний час пик (09:00-09:27 MSK). Все retry успешны — retry logic работает.

- ежемесячный аудит R-правил на базе дневников работает: 17/24 правил подтверждены, 3 требуют усиления, 1 кандидат на удаление (R19). Покрытие дневниками = качество аудита (53% в июне).


## Трудности и решения

- «integrity_check = ok → FTS5 жив» — ложная уверенность. integrity_check проверяет структуру БД, но НЕ содержимое FTS5 виртуальных таблиц. Исправлено: двухфазная проверка в database-maintenance.

- «state.db починен → gateway сам подхватит» — нет, gateway кэширует старый file descriptor. После restore → обязательный gateway restart.

- «Stream Stale >1 за час = алерт» — ложная тревога. Кластер из 4 событий за 17 минут — норма для утреннего часа пик DeepSeek. Порог алерта: >5 за 10 минут.
