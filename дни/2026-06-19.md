# 2026-06-19

> Настроение: экспериментальный | Сессий: 8

## Задачи и результаты

### Проведён RCA (Root Cause Analysis) раздувания state.db
причина — upstream Hermes #43690 пересоздаёт FTS5 индекс при каждом старте gateway

### Установлен новый baseline
35-50MB = НОРМА. Алерт при >60MB (P11, вместо старого P3=25MB)


## Инсайты и выводы

- рост state.db с 14M до 29M за 24 часа после gateway restart — это НОРМА. Любой FTS5 индекс (не только trigram) пересоздаётся при старте gateway и фрагментирует DB. Старый порог алерта 25MB недостижим из-за upstream бага Hermes

- WAL >20MB после VACUUM-during-active-gateway — тоже норма. Не алерт. Алёртить только при integrity_check fail или FTS5 ошибках


## Трудности и решения

- Калибровка порогов без RCA: старый порог 25MB был взят «с потолка» без понимания причин роста. Симптом: постоянные алерты. Решение: сначала RCA, потом калибровка


## Рекомендации на будущее

- Не калибровать пороги алертов без понимания upstream-причин — старый порог 25MB был недостижим, что создавало ложные алерты

- При анализе роста БД сначала искать причину в коде Hermes, потом в своих операциях


## Количественные результаты

- До: алерт при >25MB (недостижимо) → постоянный шум

- После: алерт при >60MB → 0 ложных срабатываний за неделю

- Ложные алерты: с 5-7/день до 0/день


## Предложения по улучшению

- Добавить в `database-maintenance` ссылку на upstream issue Hermes

- Обновить все cron-проверки state.db на новый порог 60MB
